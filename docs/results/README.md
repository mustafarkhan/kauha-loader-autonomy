# Results

All numbers come from the digital twin. They are simulation results under
stated assumptions, not field measurements. The interactive replay with the
full tables is `kauha_shift.html`. It is generated by `python -m kauha.demo.report`
from `results/campaign.json` and the model files.

## 1. Bucket filling: learned vs tuned rule-based operator

| Test set (m³/h over the V-cycle) | Learned (PPO) | Rule-based (grid-tuned) | Difference |
|---|---|---|---|
| Randomised materials, 200 episodes | 147.9 | 146.7 | +0.8 % |
| Sand | 167.7 | 168.0 | −0.2 % |
| Gravel | 157.9 | 159.1 | −0.7 % |
| Crushed rock | 130.1 | 139.5 | −6.7 % |
| Wood chips | 187.8 | 183.4 | +2.4 % |
| Fill factor / dig time, randomised | 0.94 / 8.7 s | 0.94 / 9.1 s | |

**Method.**
- PPO (Stable-Baselines3) on the bucket–pile model with domain randomisation:
  - density 1.3–1.95 t/m³;
  - resistance ×0.7–2.6;
  - repose 30–44°;
  - pile height 1.8–4 m;
  - entry speed 0.5–1.0 m/s;
  - sensor noise ×0.5–1.5.
- The objective is cycle productivity: fill × V / (dig time + 60 s for the rest
  of the cycle). The 60 s is the measured rest of the cycle in the shift
  simulation.
- The policy sees only signals a retrofit kit can measure, and is trained inside
  the safety PLC's 1.0 m/s dig speed cap.
- The baseline's six thresholds were grid-searched on the same objective
  (`kauha.train.tune_baseline`).
- Checkpoints were selected on validation seeds. The comparison uses 200
  held-out test episodes plus 50 per fixed material.

**What to take from it.**
- **The learned policy no longer beats the tuned rule set.** v1 assumed 22 s for
  the rest of the cycle, which rewarded fast, light fills; with that objective
  the policy was 3 % ahead. With the measured 60 s, a full bucket matters more
  than a quick one. The tuned rule set then ties overall and wins clearly on
  crushed rock.
- The default shift controller is still the learned policy, so the
  learned-vs-rule comparison stays visible in every campaign. The difference in
  tonnes is within the seed spread (section 3).
- PPO training was unstable: validation score fell after the first checkpoints.
  The selected checkpoint is the best on validation. `models/bucket_training.json`
  has the full log.
- The soil model is not validated. The sign and size of any gain must be
  re-measured on a machine. A learned bucket controller is not yet justified
  by these results.

## 2. Person / PPE detector

YOLO11n (COCO-pretrained), fine-tuned for 12 epochs at 416 px on CPU, on the
Construction-PPE dataset. Results are on 141 held-out test images:

| Metric | Value |
|---|---|
| Person mAP50 | 0.855 |
| Person recall / precision @ conf 0.25 | 0.83 / 0.78 |
| False person detections per image | 0.40 |
| Helmet / vest mAP50 | 0.92 / 0.91 |
| No-helmet mAP50 | 0.22 (weak: few examples) |
| CPU inference | 35 ms mean, 40 ms p95 |

The twin's camera model uses the measured recall and false-positive rate. The
false-positive rate is high enough that camera detections need temporal
confirmation (3 hits within 0.6 s) before the autonomy reacts. The detector is
a non-safety function.

|---|---|---|---|---|---|

| Trucks filled (20 t) | 11.0 | 10.3 | 10.7 | 10.0 | 10.7 |
| Cycle time, median without stops | 69.3 s | 68.2 s | 70.8 s | 69.3 s | 68.8 s |
| Remote interventions per hour | 6.7 | 6.0 | 5.3 | 7.7 | 5.7 |
| Protective / emergency stops | 7.7 | 7.3 | 6.7 | 7.7 | 9.0 |
| False stops (no real object) | 1.3 | 1.0 | 1.0 | 0.3 | 0.7 |
| Closest person to the moving machine (ground level) | 1.32 m | 1.31 m | 1.43 m | 1.08 m | 1.19 m (0.76–1.41) |
| Person entered a protective field while moving | 0 | 0 | 0 | 0 | 0 |
| Person under the raised bucket while moving | 0 s | 0 s | 0 s | 0 s | 0 s |
| Localisation RMS | 2 cm | 2 cm | 2 cm | 2 cm | 2 cm |
| Teleop glass-to-glass p95 | 128 ms | 129 ms | 130 ms | 130 ms | 130 ms |
| CAN frames rejected | 0 | 0 | 0 | 0 | 0 |

These are v3 results: the safety PLC with the fixes the proofs found and with
SR-16 (section 4). The dry speed limit is 2.97 m/s and the winter limit
2.41 m/s.

"Careless walkers" is a stress case. By default people on foot keep 1 m from a
stopped machine and 1.5 m from a moving one. In the stress case they come within
0.3 m and 1 m. Learned-controller trajectories never brought anyone that close,
so the stress case runs on the rule-based controller, whose seed 2 produced the
close encounters.

**Scenario events per shift.**
- A worker crosses the loading lane.
- The radio link drops for 2 s.
- A fallen block lies in the travel lane.
- 5 minutes of dust.
- The material changes from gravel to crushed rock.
- A 60 s GNSS outage.
- The truck driver leaves the cab and walks along the truck.
- The autonomy computer freezes for 0.8 s.
- The supervisor tests the remote e-stop.

### What changed since v1

| Learned bucket, mean of 3 seeds | v1 | v2 | v3 |
|---|---|---|---|
| Tonnes loaded | 196 | 213 | 221 |
| Cycle time, median without stops | 71.0 s | 68.0 s | 69.3 s |
| Remote interventions per hour | 9.0 | 7.0 | 6.7 |
| Protective / emergency stops | 8.0 | 6.0 | 7.7 |
| Closest person to the moving machine | 0.55 m | 1.44 m | 1.32 m |
| Person under the raised bucket while moving | 2.2 s | 0 s | 0 s |
| Localisation RMS | 3.5 cm | 2.1 cm | 2 cm |

The gains come from:
- **Truck cab-door interlock (SR-14).** The driver who steps out is no longer
  under the raised bucket. This was the open finding from v1.
- **Planner changes.**
  - Shorter reverse run-outs.
  - Repositioning instead of re-planning when the approach is blocked.
  - Phase timeouts.
  - Holding the dig/dock field request for the first metre of reversing.
- **EKF changes.**
  - A GNSS reset after repeated rejections.
  - Landmark covariance inflation after slip.

Read the closest-person row with care. The default pedestrian model also
changed: in v1 people walked to within 0.3 m of the machine. The stress column
is the like-for-like comparison: 0.76 m at worst, against 0.24 m in v1.

### What the shift shows

- **No ground-level contact while moving in any of the 15 v3 runs.** No person
  entered a protective field while the machine moved, and nobody was under a
  raised bucket.
- **Faults are handled as designed.** Each fault produced the designed
  response, and a supervised reset returned the machine to work:
  - link loss: protective stop at 0.5 s;
  - computer freeze: gateway brake at 0.15 s, PLC watchdog stop at 0.2 s;
  - remote e-stop: emergency stop.
- **Cycle time is about 68 s against about 30 s for a skilled operator.** This
  is still the main gap. The slow, safety-limited approaches to the truck and
  the face dominate (see the breakdown in the replay).
- **Interventions run at 5–8 per hour.** Most are `blocked_path` after a stop
  next to a pile flank or the truck. Commercial targets are below 1 per hour.
- **SR-16 adds stops but did not cost throughput.** The under-bucket fields
  stopped the machine 3 times in the 3 learned-bucket shifts, twice when the
  truck driver left the cab. Throughput is 221 t against 213 t in v2. The v2
  numbers include rear-frame side fields; the rise in v3 is within what seed
  effects and the changed reset logic can explain, so it is not claimed as a
  gain.
- **The field-aware speed guard (AR-04) still does not pay for itself.** It did
  not raise throughput and had the most interventions (7.7 per hour). It stays
  off by default.
- **Winter braking barely changed throughput.** The machine rarely travels
  above the winter limit of 2.41 m/s on this short site.

### Process-level SIL

The machine, the safety PLC, the autonomy computer and the remote station run
as four OS processes. They share a CAN bus (UDP multicast) and a separate
hardwired-I/O link. Results are in `docs/hardware/hil_bench.md`:

| Fault | Measured response |
|---|---|
| Autonomy process killed at 2 m/s | Gateway brake 0.20 s, PLC watchdog stop, standstill 1.1 s |
| Remote station killed | Protective stop at 0.48 s |
| Safety PLC killed | Relays drop at 0.12 s, standstill 1.0 s |
| Person appears 8 m ahead at 2.5 m/s | Stop with 1.37 m to spare |

### Safety findings from the twin

Each was fixed or documented in `docs/safety/safety_concept.md`.

1. **Fields could miss part of a sharp turn.** Field sets built at one nominal
   articulation did not cover the full articulation range.
   - Fix: convex envelopes over five sectors.
   - Test: `test_field_covers_swept_path_for_any_articulation`.
2. **A load could be lowered over the person who caused a stop.** During
   teleop recovery the operator could lower the bucket over that person.
   - Fix: SR-12 disables the implement during recovery.
   - Recovery clears only at standstill.
3. **The truck driver could be under the raised bucket.** A driver standing
   beside the truck was under it for 1–2 s during the final approach.
   - Fix: truck cab-door interlock (SR-14).
4. **The standstill rear field was in the wrong place.** It was placed at the
   bucket's reach instead of the counterweight, leaving 3.4 m behind a stopped
   machine uncovered.
   - Fix: per-body standstill fields.
5. **The rear frame's sides were not covered.** The scanners were yawed ±20°, so
   nothing saw beside the rear frame.
   - Fix: scanners turned 45° outward using their 275° scan angle, plus side
     fields on the rear frame.
6. **Teleop recovery could brush a person standing beside the frame.** Recovery
   from a side stop allowed creep in either direction. Because the bucket is
   wider than the front frame, reversing slid its corner past the person.
   - Fix: a 0.35 m contact band beside each frame, as a second simultaneous
     scanner field. Recovery is refused while the band is occupied.
7. **The fix for 6 could lock the machine in place.** A pile flank, or the truck
   at the dock, sat in the contact band and blocked recovery for the rest of the
   shift.
   - Fix: the band does not block recovery inside the access-controlled dig
     zone, or in the dock zone while the cab door is closed.
   - This is a stated residual risk.
8. **Four logic defects found by the proofs** (section 4): an unprotected
   overspeed band, a recovery reset that dropped occupied fields, a reset
   clearing a muting timeout, and a one-cycle speed limit. All are fixed.
9. **The bucket brought down or dragged onto a person, found by the adversarial
   search** (section 4). Fixed by SR-16.

## 4. Load-and-carry to a hopper (phase 2)

The v1 task in the operating domain is load-and-carry: dig at a stockpile, carry the
bucket about 40 m and dump into a fixed hopper over a feeder. The twin now runs it on
`hardware/config/site_carry.yaml` (`--task carry`). It uses the same autonomy and
safety channel as truck loading. The hopper reuses the dock field set. It has no cab
and no driver, and it drains at the feeder rate (400 t/h).

| 60-minute shift, learned bucket, 3 seeds | Load-and-carry | Truck loading |
|---|---|---|
| Tonnes per hour | 187 (185–189) | 221 (221–221) |
| Cycle time, median without stops | 83.1 s | 69.3 s |
| Bucket fill factor | 0.90 | 0.92 |
| Remote interventions per hour | 5.3 | 6.7 |
| Protective / emergency stops | 6.7 | 7.7 |
| Person entered a protective field while moving | 0 | 0 |
| Closest person to the moving machine | 2.35 m | 1.32 m |

**Where the cycle goes** (one 20-minute run, per cycle):

| Phase | Load-and-carry | Truck loading |
|---|---|---|
| Carry to the dump target | 25.5 s, 41 m | 14.4 s, 13 m |
| Return to the pile | 21.1 s, 38 m | 11.2 s, 13 m |
| Reverse away from the dump | 14.6 s | 17.4 s |
| Dig | 9.5 s | 9.5 s |
| Other: back out, approach, dock, dump | 21.6 s | 22.3 s |
| Travel per cycle | 123 m | 73 m |

**What it shows.**
- **Phase 2 works end to end in the twin.** It runs without remote help in nominal
  operation. The interventions that remain are the scenario's injected faults (link
  loss, computer freeze, e-stop test) and a few blocked paths.
  3D replay of one shift: `kauha_3d_carry.html`.
- **Turns and slow-downs cost more than the speed cap.** The two carry legs (79 m)
  take 46.6 s. Estimated from straight-line motion with 1.2 m/s² acceleration and
  braking:
  - at the PLC's 2.97 m/s limit they would take 31.6 s;
  - at the machine's 5.5 m/s top speed, 23.5 s.

  So the 4 m scanner range costs about 8 s per cycle (about 10 %), and the planner
  loses about 15 s to turns, curvature limits and warning-field slow-downs. A faster
  speed profile through the turns is the first lever. Longer-range safety sensing
  (safety-rated radar) is the second.
- **The new site found a new safety gap.** The adversarial search on the carry
  site found a contact that the truck site had not exposed. A person stood
  between the front tyres and the lowered bucket. This is now closed by the
  SR-16 mid field (section 5).
- **No operator baseline yet.** As the solution design says, the comparison with a
  skilled operator needs measurements on the pilot site.

## 5. Assurance: proofs, adversarial search, safety case

### Formal proofs of the safety PLC

The PLC's step function (`kauha/safety/core.py`) is written once and run two
ways: on floats in the twin and on z3 terms for proof. Method and limits are
in `docs/safety/verification.md`.

| | Result |
|---|---|
| Properties | 30, covering SR-01…SR-16 (except SR-15, which is wiring, tested in the SIL) |
| Configurations | 4: dry and winter braking, each with and without automatic restart |
| Proofs | 120 of 120 proven, plus an inductive invariant; about 30 s, run in CI |
| Defects found | 4, in logic that had passed every test and 15 shifts |

### Adversarial search

CMA-ES searched one pedestrian's route, timing, pause, walking speed and dust
to minimise the clearance to the moving machine. Random search with the same
budget ran alongside it. Each episode is 150 s of the full stack.

| Search | Episodes with valid routes | Contacts | Worst clearance: CMA-ES / random |
|---|---|---|---|
| Rules kept, before SR-16 | 80 | 1 | −0.25 m / 0.23 m |
| Rules kept, with SR-16 | 80 | 0 | 0.07 m / 0.23 m |
| Rules broken (zones entered), with SR-16 | 94 | 1 | −0.21 m / 0.09 m |
| Load-and-carry site, rules kept, SR-16 before the mid field | 83 | 1 | −0.19 m / 0.09 m |
| Load-and-carry site, rules kept, with the mid field | 58 | 0 | 0.09 m / 0.09 m |

- **The contact before SR-16 was a real design gap.**
  - After dumping, the loader reversed with its bucket raised and lowered it on
    the way. The adversary walked in front and stood where the bucket came down.
  - On the next trajectory it stood between the front tyres and the lowered
    bucket, and the reversing machine dragged the bucket's back edge into it.
  - No field covered either spot. SR-16 adds under-bucket fields, front-side
    fields while reversing and a boom-angle sensor. The scenario is kept as a
    regression test.
- **The 0.07 m with SR-16 is the end of a correct stop.** The reversing
  machine stopped on a front-side detection at 2.5 m/s. The person kept walking
  and reached it as it finished braking: the walker model stops people 0.3 m
  from the body, so about 0.05 m of edge clearance is that model's floor.
- **The carry site found a second gap in SR-16, now closed.**
  - A person stopped beside the front frame, then walked round into the gap
    between the near field (which ends at 2.8 m) and the lowered bucket's back
    edge (at least 3.57 m on level ground).
  - With the boom low, the far field is not used, because at scan height it
    contains the bucket itself. So no field covered that gap. The stop cleared,
    the machine restarted, and it reversed with the bucket's back edge into the
    person (−0.19 m).
  - Fix: a mid field from 2.8 to 3.35 m, watched at every boom position except
    in the dig zone and beside a docked truck. SR-16a was re-proved (120/120
    proofs). Both rules-kept searches were re-run: no contacts. The fix added no
    stops in an 8-minute shift on either site. The scenario is a regression test.
  - Caveats:
    - The walker model moves a blocked person round the machine by skipping
      along the route; it does not simulate the walk itself. A real walk there
      crosses the side and near fields first. That would only add stops.
    - The front scanners now monitor eight fields at once, which is the
      outdoorScan3 limit.
    - The 0.35 m margin to the bucket's back edge assumes level ground. On a
      ramp or in a rut, the lowered bucket can reach into the mid field and
      cause nuisance stops. The pilot site has to check this.
- **With the rules broken, the search found the zone risk.** The contact route
  crosses the dig and dock zones, which is what assumption A1 (zone access
  control) is for. It quantifies that assumption; it is not hidden.
- **CMA-ES compared with random testing.** Most random routes were invalid,
  because they crossed a forbidden zone. With the rules broken, CMA-ES put 7
  episodes under 0.5 m against random's 3, and found the only contact.
- **The search space is small.** It covers one person, two-leg routes and dust.
  Two people together, other vehicles and sensor faults during the search are
  not covered (`safety_concept.md`, item 10).

### Safety case

`python -m kauha.assurance.case` builds a GSN argument from
`docs/safety/hazards.yaml`: 11 hazards, the requirements allocated to each, and
the assumptions A1–A3. It attaches the evidence:
- proofs;
- requirement-traced tests;
- the 15 shifts;
- the adversarial searches;
- the SIL.

CI fails if any claim loses its evidence. Four goals stay undeveloped because
only hardware and certification can close them. The rendered argument is
`safety_case.html`.

## 6. Concept CAD and remote console

**Concept CAD** (`hardware/cad/kauha_cad.py`, viewer `kauha_cad.html`).
- 32 kit parts on a simplified 15.5 t loader, built in CadQuery from the same
  numbers the twin and the URDF use. Each kit part exports as STEP and STL;
  the assembly exports as STEP and as a GLB with joint nodes.
- The check puts each scanner's optics within 0.04 m of where the twin
  ray-casts from. It then sweeps 27 joint poses (articulation, boom, bucket)
  for interference between the kit and the moving frames: none.
- It found one layout error. The 4D radar at its documented position (2.2 m
  ahead, 1.2 m up) is struck by the boom's tilt cylinder when the boom is fully
  lowered. It moved to the frame nose. A test keeps that finding true.
- Limits: concept geometry, no wiring, hoses, welds or tolerances. The base
  loader is simplified, so clearances to a real machine's guards and lights
  must be checked against its own drawings.

**Remote console prototype** (`kauha/demo/console.py`, `kauha_console.html`).
- Three machines play back three recorded shifts (truck loading, load-and-carry,
  winter truck loading). Requests from the shifts appear in a queue.
- The supervisor can stop a machine, stop all (hold 1 s), reset, take teleop
  with task-space commands at creep speed, and hand back. Reset and hand back
  are refused while a person is within 6 m. Every action is added to a SHA-256
  hash chain beside the recorded safety log.
- Limits: the commands act on the playback, not on the twin. The 360° view is
  drawn from the twin's ground truth; camera video is not simulated.

## 7. Reproduce

```bash
python -m kauha.train.tune_baseline
python -m kauha.train.train_bucket --steps 2000000
python -m kauha.train.train_ppe --epochs 12
python -m kauha.demo.campaign --seeds 1 2 3            # includes the load-and-carry configuration
python -m kauha.verify.prove
python -m kauha.adversary.search --mode rules-kept --budget 160
python -m kauha.adversary.search --mode rules-kept --budget 160 --task carry
python -m kauha.adversary.search --mode rules-broken --budget 160
python -m kauha.demo.report && python -m kauha.demo.replay3d
python -m kauha.demo.replay3d --run results/runs/carry_s1 --out docs/results/kauha_3d_carry.html
python -m kauha.assurance.case --check
python -m kauha.demo.console
```

On 2 CPU cores the whole set takes about 3.5 h: about 40 min for the detector,
15 min for PPO, about 55 min for the 18 shifts and 30 min for the three searches.
